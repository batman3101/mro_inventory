# 배포 절차서 — Supabase Auth 전환 (감사 2026-11-27 수정분)

브랜치: `fix/audit-2026-11-27`

**순서가 중요하다.** 2단계 마이그레이션(익명 차단)을 새 화면 배포보다 먼저 적용하면 현재 사이트가 즉시 멈춘다.
각 단계는 사용자 승인 후 진행한다 (운영 DB 적용·main 병합).

## 0. 사전 준비

- [ ] 운영 DB 백업 (Supabase 대시보드 → Database → Backups, 또는 `pg_dump`)
- [ ] Supabase 대시보드 → Authentication → Sign In / Providers → **"Allow new users to sign up" 끄기**
      (켜져 있어도 앱 데이터에는 접근 못 하지만, 불필요한 계정 생성을 막는다)
- [ ] 공장 지정 확인: `location_id` 가 지정된 계정은 적용 후 **그 공장만** 보게 된다.
      2026-11-27 기준 admin 3명이 모두 ALT 지정 → ALV 도 봐야 하는 계정은 사용자 화면에서 공장을 비워 둔다.
- Vercel 환경변수 추가 없음 (기존 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_KEY` 사용)

## 1. 1단계 마이그레이션 — `20261127000100_auth_foundation.sql`

추가만 하는 변경이라 현재 사이트는 계속 동작한다.
예외: 현재 사이트의 **단가 Excel 일괄등록 / 품목 수정 중 단가 저장**은 3단계 배포 전까지 실패할 수 있다
(단가 UNIQUE 키에 공장이 추가되어 옛 코드의 upsert 기준이 사라짐). 이 구간을 짧게 유지한다.

## 2. 계정 연결 — `scripts/migrate-users-to-auth.mjs`

```powershell
node scripts/migrate-users-to-auth.mjs          # 미리보기 (변경 없음)
node scripts/migrate-users-to-auth.mjs --apply  # 실제 연결
```

- 기존 비밀번호 해시를 그대로 옮기므로 **비밀번호 재설정은 필요 없다.**
- 4명 모두 `연결 완료` 또는 `이미 연결됨` 이어야 다음 단계로 간다. 다시 실행해도 안전하다.
- **0단계의 가입 차단을 먼저 끈 뒤 실행한다.** 같은 이메일의 auth 계정이 이미 있으면 (스크립트가 만든 것이 아닌 한)
  자동 연결하지 않고 `자동 연결하지 않음` 오류로 멈춘다 — 누군가 관리자 이메일로 먼저 가입해 계정을 가로채는 것을 막기 위해서다.
  이때는 Supabase 대시보드 → Authentication → Users 에서 그 계정이 누구 것인지 확인하고 삭제한 뒤 다시 실행한다.

## 3. 새 화면 배포 (main 병합 → Vercel)

- 배포 후 모든 사용자는 **한 번 다시 로그인**해야 한다 (예전 로그인 상태는 더 이상 인정하지 않음).
- 확인: 각 계정으로 로그인 → 공장 선택 버튼, 재고·입출고 목록, (system_admin) 사용자 화면.

## 4. 2단계 마이그레이션 — `20261127000200_auth_lockdown.sql`

3단계 확인이 끝난 뒤에 적용한다. 익명 접근과 옛 정책을 제거하고, 기존 수정·삭제 RPC 에 권한 검사를 넣는다.

- 확인: 로그아웃 상태에서 데이터가 보이지 않는지, 각 계정의 공장 범위·읽기 전용(viewer)이 맞는지.

## 되돌리기

| 시점 | 방법 |
|---|---|
| 1~3단계 사이 | 이전 배포로 Vercel 롤백. 1단계 변경은 추가만이라 옛 화면과 함께 동작 (단가 일괄등록 예외) |
| 4단계 이후 | 옛 화면은 익명 접근에 의존하므로 롤백하려면 익명 권한을 다시 열어야 한다 — 보안 구멍을 되살리는 것이므로 권장하지 않음. 새 화면에서 문제를 고친다. |
