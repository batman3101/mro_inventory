### RESTYLE-01 — 깨진 테마 저장값으로 빈 화면 → 수정

**재현 (감사 대상 `94d837e`).** 지적 그대로다. 저장값이 `"invalid"`, `null`, 숫자 `1`, 객체일 때 이메일 입력칸 0개, 화면 글자 0자,
`TypeError: Cannot read properties of undefined (reading 'accentWeak')`.
감사 보고서에 없던 경우도 하나 찾았다: 값이 `"__proto__"` 이면 화면은 뜨지만 `data-theme="__proto__"` 가 되어 PC 가 다크인데 라이트로 나왔다.
반대로 깨진 JSON, `null`, 빈 문자열, 배열, 버전 불일치는 고치기 전에도 문제없이 `system` 으로 떴다 (zustand 가 읽기 실패를 스스로 넘긴다).

**원인.** `src/store/theme.store.ts` 가 저장값을 확인 없이 상태에 넣었다. TypeScript 의 `ThemeMode` 타입은 localStorage 안의 글자를 검사해 주지 않는다.
그 값이 `palettes[name]` 조회에 그대로 쓰여 `undefined` 가 됐고, 이 코드가 화면 전체를 감싸는 자리에 있어 로그인까지 사라졌다.

**수정.**
- `theme.store.ts`: 저장값을 합치는 `merge` 에서 세 값이 아니면 `system`.
- 같은 파일 `resolveTheme()`: `light`·`dark` 만 "선택"으로 보고 나머지는 전부 PC 설정을 따르게 함 (어떤 값이 들어와도 `light` 아니면 `dark` 만 나온다).

**검증 (개발 서버·배포용 빌드 각각, PC 설정 다크).** 저장값 17가지 — 정상 3 + 비정상 14 (잘못된 문자열, `null`, 숫자, 객체, `__proto__`, `state` 가 null/없음/문자열, 깨진 JSON, JSON `null`, 배열, 일반 글자, 빈 문자열, 버전 불일치) —
전부 이메일 입력칸 1개, 페이지 오류 0건, 테마는 정상값이면 그 값·아니면 PC 설정(다크).

### RESTYLE-02 — 변경 전 창 스크린샷이 로그인 화면 → 수정

**재현.** 파일 해시로 확인했다. `before-{light,dark}-ko-modal-item.png` 2장의 SHA256 이 `before-light-ko-login.png` 와 같았고 (`faf64e6b…`),
`before-{light,dark}-ko-modal-outbound.png` 2장은 필수 입력 오류가 뜬 로그인 폼이었다.

**원인 (감사는 코드 대조로 추정, 여기서는 기준 커밋을 띄워 직접 확인).** 도구가 `button.ant-btn-primary` 의 첫 번째를 눌렀다.
기준 커밋 `b906fb4` 의 `/items` 에서 그 순서는 `["로그아웃","ALT","🇰🇷","소모품 추가"]` 였다. 즉 "소모품 추가" 대신 사이드바의 로그아웃을 눌렀고, 누른 뒤 주소는 `/login` 이었다.
변경 후 화면은 상단에 주요 버튼이 없어 같은 선택자가 맞게 동작했기 때문에 "변경 후" 스크린샷은 영향이 없었다. 찍기 전에 화면을 확인하는 단계가 없어서 틀린 화면이 그대로 저장됐다.

**수정 (`docs/restyle/tools/shoot.mjs`).**
- 버튼을 페이지 영역 안에서 **이름으로** 찾는다. 이름은 앱의 번역 파일(ko/vi)에서 읽는다.
- 찍기 전에 **주소**, **페이지 제목**, **창 제목**을 확인하고 다르면 오류를 내고 멈춘다. 로그인 폼이 보이면 바로 실패한다.
- 문제의 4장을 기준 커밋 `b906fb4` 에서 다시 찍어 교체했다. 이제 로그인 화면과 해시가 다르고, 직접 열어 "소모품 등록"·"새 출고" 창임을 확인했다.

**검증.**
- 고친 도구로 기준 커밋의 "변경 전" 40장 전체를 다시 돌림: 모두 통과. 즉 나머지 36장은 처음부터 맞는 화면이었다 (파일은 교체하지 않음).
- 고친 도구로 수정 후 코드의 "변경 후" 58장 전체를 다시 돌림: 모두 통과, 글자 잘림 0건.
- 반대 시험: 기대하는 창 제목을 일부러 틀리게 주면 `exit 1`, `Error: the window "…" did not open`.

**정정해야 하는 이전 보고.** "98장 증거" 중 4장은 목표 화면이 아니었다. 변경 전 글자 잘림 9곳이라는 수치는 화면(표) 기준이라 그대로 맞다 (다시 돌려 한국어 3·베트남어 6 확인).
`docs/restyle/README.md` 에 정정 내용을 적었다.

### RESTYLE-03 — 떠 있는 알림이 테마 전환을 따르지 않음 → 수정

**재현 (실제 앱, 로그인 뒤).** 앱이 쓰는 antd 모듈로 닫히지 않는 알림을 하나 띄우고 사이드바의 테마 전환을 눌렀다.
다크로 바꿔도 알림은 글자 `rgb(28, 34, 48)` / 바탕 `rgb(255, 255, 255)` (라이트 색) 그대로였다. 감사 보고서의 수치와 같다.

**원인.** `message.success()` 같은 호출은 antd 가 따로 만든 화면 조각에 그려진다. 거기에 "그 순간의 테마"를 넘겨 두기만 해서, 테마가 바뀌어도 그 조각은 다시 그려지지 않았다.

**수정 (`src/AntConfigProvider.tsx`).** 그 조각 안에 테마 저장소와 언어를 **직접 구독하는** 작은 컴포넌트(`StaticHolder`)를 둔다. 테마가 바뀌면 스스로 다시 그린다.

**검증 (개발 서버·배포용 빌드).** 알림을 띄운 채 라이트 → 다크 → 라이트 → 다크 → 시스템 순서로 전환: 매번 알림 색이 화면 테마와 같다
(다크일 때 글자 `rgb(227, 231, 237)` / 바탕 `rgb(23, 27, 33)`). 언어를 KO → VI 로 바꿔도 알림은 그대로 떠 있다. 페이지 오류 0건.

**한계.** 확인한 것은 `message` 다. `notification` 과 정적 `Modal.confirm` 은 이 앱에서 쓰지 않아 확인하지 않았다 (같은 경로를 쓰므로 같이 고쳐졌을 것으로 보지만 추정이다).

### RESTYLE-04 — 앱이 뜨기 전 반대 색 화면 → 수정

**재현.** 지적 그대로다. 앱의 시작 스크립트 응답을 붙잡아 두고 보면 `data-theme` 이 없고 바탕색도 없어서, 저장은 라이트인데 PC 가 다크면 어두운 빈 화면이 먼저 보였다.
(이전 보고에서 "추정"으로 적었던 것이 실제임을 확인.)

**원인.** 디자인 값(CSS 변수)과 `data-theme` 을 앱의 JS 가 실행될 때 만들었다. JS 가 도착하기 전에는 브라우저가 PC 설정대로 바탕을 칠한다.

**수정.**
- `vite.config.ts` 에 `theme-boot` 를 추가: 빌드할 때 `index.html` 의 `<head>` 에 ① 디자인 값 CSS 와 바탕색 ② 저장한 테마를 읽어 `data-theme` 을 정하는 짧은 스크립트를 넣는다.
- 그 내용은 `src/styles/themeBoot.ts` 가 `tokens.ts` 에서 만든다. **색 값은 여전히 `tokens.ts` 한 곳에만** 있고 `index.html` 에 직접 적은 색은 없다.
- 스크립트의 규칙은 RESTYLE-01 과 같다 (`light`·`dark` 만 선택, 나머지는 PC 설정). 깨진 저장값도 여기서 걸러진다.
- `theme.store.ts` 가 실행 중에 `<style>` 을 끼워 넣던 코드는 없앴다 (같은 내용이 두 번 들어가지 않게). 쓸모없어진 `color-scheme` 메타도 뺐다.

**검증 (개발 서버·배포용 빌드, 시작 스크립트 응답을 붙잡아 둔 상태).** 7가지 조합 — 저장 라이트+PC 다크, 저장 다크+PC 라이트, 시스템×2, 저장 없음, 잘못된 값, 깨진 JSON —
모두 앱이 뜨기 **전에** `data-theme` 과 바탕색이 최종 값과 같다 (라이트 `rgb(233, 237, 242)`, 다크 `rgb(14, 17, 21)`).

**한계.** 실제 배포망에서 깜빡임이 사라졌는지를 눈으로 잰 것은 아니다. "JS 가 늦게 오는 동안 무엇이 칠해지는가"를 응답 지연으로 분리해 본 검사다.
브라우저가 `localStorage` 를 막아 둔 경우는 PC 설정을 따른다 (코드상 그렇고, 따로 시험하지는 않았다).

## 4. 남은 한계와 확인하지 못한 것

- 브라우저는 Chromium 하나로만 확인했다.
- 실제 Google Fonts 가 내려온 상태의 글꼴은 이번 검증 대상이 아니다 (이전과 같음).
